Setup

swe init

Create ~/.swe and symlink every harness to it

  swe init                    Create the layout and link all harnesses
  swe init --full             List every path, not just the counts
  swe init --check            Show what would change, write nothing (alias: -n)
  swe init --force            Replace real files too (backed up first)
  swe init --migrate          Move a pre-0.2.7 ~/.config/swe into ~/.swe
  swe init --yes              Register every new harness without asking
                               (also the non-terminal default)
  swe init --hub=<git url>     Clone your hub repo as ~/.swe first, then link
                               (only while ~/.swe has no hub: no AGENTS.md, no .git)
  swe init --accounts         Only sync the extra account homes the
                               accounts.sync.* switches name (takes --check, --json)

  Collision: -n means dry-run here and on swe install, but fetch-fresh-data on swe list.

  A symlink is a shortcut file: each harness's folder points at the one
  real copy in ~/.swe, so editing once updates it everywhere.

New harnesses
  Found via their skills folder. Ticked ones are registered and linked,
  instructions included; unticked ones are archived in harness.json and
  left alone. swe hs archives or stars them later.

What it owns
  ~/.swe/AGENTS.md   one instruction file, linked in under each harness's
                        own name (CLAUDE.md, QWEN.md, CRUSH.md, GEMINI.md)
  ~/.swe/skills/     one skill tree, linked in as every harness's skills/
  ~/.swe/hooks/      hook scripts, one folder per harness (hooks/claude/),
                        each script linked into that harness's hooks dir;
                        declaring the hook in its settings stays with you
  ~/.swe/.linkignore paths to leave alone, one gitignore-style pattern per
                        line, e.g. .agents/skills or .config/*/AGENTS.md
  ~/.swe/backups/    anything replaced, timestamped

States
  linked    already points at the canonical file
  create    nothing there yet, will symlink
  relink    symlink pointing elsewhere, will repoint
  conflict  a real file or directory, needs --force
  skipped   harness not installed on this machine
  ignored   listed in .linkignore or archived in harness.json,
               never touched or counted

swe instructions

Compile shared instruction chapters into ~/.swe/AGENTS.md

  swe instructions init     Fold the current AGENTS.md into a first chapter
  swe instructions build    Build the complete shared instruction file
  swe instructions check    Exit 1 if the generated file is missing or stale
  swe instructions watch    Build now, then rebuild on source changes

  Edit chapters under ~/.swe/AGENTS_MD/ and list their relative .md
  paths in index.txt, in order. Blank lines and # comments are ignored.
  Build writes ~/.swe/AGENTS.md atomically, only when its SHA256 changes.
  Check writes nothing. Watch reports source errors and keeps waiting; Ctrl-C stops it.
  Harness symlinks keep pointing at the generated AGENTS.md. Edit the chapters,
  not the generated file. A running chat may need a new chat to read the update.

  build, check and init take --json for the app's document.

swe setup

Sectioned setup wizard for SWE

  swe setup                    Run all six interactive setup stages
  swe setup --quick            Only visit missing or actionable stages
  swe setup harnesses          Discover and register coding CLIs
  swe setup providers          Review provider credential coverage
  swe setup mcp                Import MCP servers into mcp.json
  swe setup skills             Unify safe roots under ~/.swe/skills
  swe setup report             Configure summarizer and writer models
  swe setup check              Verify the resulting setup

  Returning-user prompts show current values; Enter keeps them. SWE creates a
  timestamped backup before changing harness.json, mcp.json, or config.json.

  swe setup --apply            Apply safe discovery changes without prompts
  swe setup --json             Print the discovery preview as JSON
  swe setup --non-interactive  Preview without prompts or writes
  swe setup --hub=<git url>    Clone your hub repo as ~/.swe first, then
                               run any of the above (only while ~/.swe has no hub yet)

  While ~/.swe has no hub yet (no AGENTS.md, no .git), the wizard first asks
  for your hub repo's URL; a blank answer starts an empty hub.

  Provider credentials remain external. Use swe providers info <name> for the
  expected key file and environment variable; harness OAuth remains harness-owned.

swe config

View or update SWE configuration

  swe config                     Print resolved configuration
  swe config get <key>           Print one resolved dotted key
  swe config set <key> <value>   Save a string, number, boolean, or JSON array
  swe config unset <key>         Remove a user-set value
  swe config edit                Open ~/.swe/config/config.json in VISUAL or EDITOR
  swe config check               Validate types, report setup, and secret safety
  swe config setup report        Configure cheap summary and strong writer models

Examples
  swe config set report.session.harness claude
  swe config get report.writer.model
  swe config unset report.session.model

SWE never stores model credentials in this file. Claude and Codex continue
to use their own login state and environment.

swe doctor

Diagnose Node/PATH issues that hide global installs

  swe doctor                   Report node/npm, global bin PATH, nvm, off-PATH tools
  swe doctor --json            Findings as JSON: ok, plus check, severity, message, fix
  swe doctor --fix             Run every safe local fix, then check again
  swe doctor --fix=<check>     Only findings under that check (setup, drift.hooks)
  swe doctor --fix --dry-run   Show what --fix would run, run nothing (alias: --check)
  swe doctor --fix=<check> --message=<text> [--action=<a>]
                               Run one finding's fix, as a Run button does

  Plain swe doctor only reads. --fix runs the local repairs
  in order (setup, discover, init, plugin-fix), reading the report again
  after each, and prints what it fixed and what is left. Installs, plugin
  reinstalls, MCP entry overwrites (mcp-sync) and the drops that delete
  entries or links (undeclare, marketplace-drop, dangling-link) never run
  in a batch: they run only
  for one finding named with --message. With --json, --fix prints
  {dry_run, ran, fixed, still_failing, skipped, not_cleared, fixable_left}.

  Doctor also reports plugin drift (swe find plugins) as plugins.*,
  broken top-level links in ~/.swe, and MCP servers failing a local
  check (swe mcp doctor without the network) as mcp.server, each with
  its fix.

  Catches the common failure mode: npm install -g under nvm while
  interactive/non-interactive shells use Homebrew Node (tool missing from PATH).

  Also runs read-only drift checks: places two parts of quiver were supposed
  to agree and quietly did not — help text vs dispatch, registry shape,
  hardcoded fallback tables vs harness.json, dangling symlinks. A finding
  looks like:
    ! [registry] cursor: state 'disabled' is not one of ['active', 'archived', 'starred']

Exit codes
  0  healthy
  1  off-PATH tools, global bin not on PATH, or an error-severity drift
     finding. Warn-level drift (stale help, code-table mismatches, symlink
     notices) is printed but does not fail the exit code.
  With --fix: 0 when every fix worked and none in scope is left; findings
  that need a person (logins, installs, PATH edits) do not count.

swe install

Show or run a harness's install command per package manager

  swe install <name>                    List its install commands (runs nothing)
  swe install <name> --via=<method>     Run one: brew, cask, npm, uv, nix or script
  swe install <name> --package=<pkg>    Explicit npm package (works for unknown names)
  swe install <name> --command=<cmd>    Override CLI binary name to register
  swe install <name> --dry-run          Print the command, run nothing (alias: -n)
  swe install [--json]                  Known installers as JSON (never runs)

  Methods are the package managers a harness is published through; npm uses a
  PATH-visible npm (prefers Homebrew over nvm) so the binary lands where
  swe list / swe check can see it. A name with no known
  installer is refused — swe never guesses package names.

Examples
  swe install gemini
  swe install gemini --via=npm
  swe install claude --via=cask --dry-run
  swe install mastracode --package=mastracode
  swe install --json

Registry

swe list (ls)

List all registered AI coding tools (short for swe harness list)

  swe list                     List all tools (starred first, then 100d usage)
  Short for swe harness list; every harness verb lives under swe harness.
  swe list <tag>               Filter by tag (e.g. swe list agentic)
  swe list --usage             Add 100d sessions and remaining quota
  swe list -u --exclude=a,b     Same, without polling usage for a and b
  swe list --links             Add AGENTS.MD and SKILLS link status
  swe list -n                  Fetch new session and rate-limit data
  swe list edit                Choose which columns to show
  swe list edit --reset        Restore the default columns
  swe list legend             Explain the swe list column glyphs

  Starring pins a tool to the top of swe list (★) and opts it into
  rate-limit / quota fetching — the --usage column only polls starred
  tools. It does not change what swe use, swe report, or swe session do.
  Use swe hs star <name> to favourite, swe hs archive <name> to shelve.

  Archiving hides a tool from swe list and records why; nothing gets
  uninstalled. swe list --scope=all brings it back.

Flags
  --usage / -u            Show usage. This is the only part of swe list
                          that touches the network, so it is opt-in: the plain
                          listing runs in ~70ms, --usage costs ~700ms on a cold
                          cache. Implied by --refresh.
  --links / -L            Show quiver link status instead of usage.
  --refresh / -r / -n   Bypass caches and fetch new data.
  --refresh-failed            Refetch only providers whose cached reading
                          failed (timeout, sign-in needed, a window unread);
                          healthy cached readings still serve.
  --cache-ttl=<seconds>       How fresh a cached reading must be to serve,
                          overriding the 5-minute default for this run.
  --scope=active|archived|all  Which harnesses show. Default active (archived
                          hidden); archived shows only shelved tools; all shows both.
  Collision: swe find also has a --scope, but it means something else there
  (where a file lives, not archived-visibility). In swe find, archived-
  visibility is --harness=all instead.

Link states
  ✓  linked to ~/.swe      ○  nothing there yet, or safe to absorb
  ↻  symlink points elsewhere  ✗  real file in the way, needs --force
  ○  holds files that exist nowhere else, left alone on purpose
  ·  no known convention, or harness not installed

  swe list legend prints this with each state named.
  Run swe init to link everything.

swe info

Show full details for a tool

  swe info <name|alias>        Show command, version, path, tags, aliases

Examples
  swe info claude
  swe info cc

swe add

Register a new tool in the registry

  swe add <name> <command>             Add with defaults
  swe add <name> <command> [desc]      Add with description
  swe add <name> <cmd> --aliases=a,b   Set short aliases
  swe add <name> <cmd> --tags=t1,t2    Set tags
  swe add -i                           Interactive form (walk each field)
  swe add <name> -i                    Interactive, pre-filled name
  swe add <name> <cmd> --no-replace --json  For the app: refuse existing names

  The registry is one file, ~/.swe/config/harness.json, listing every
  tool quiver knows. Adding a tool here does not install it — it tells
  quiver the tool exists, so swe list/swe use/swe edit can find it.
  If the tool already exists, it updates the entry.

Examples
  swe add aider aider "AI pair programmer" --aliases=ai --tags=agentic,coding
  swe add mytool /usr/local/bin/mytool

swe edit

Edit fields of a registered harness

  swe edit <name|alias>                Interactive field editor
  swe edit <name> --description="..."  Set description
  swe edit <name> --aliases=a,b        Replace aliases (comma-separated)
  swe edit <name> --tags=t1,t2         Replace tags
  swe edit <name> --command=<cmd>      Change launch command
  swe edit <name> --display-name="..." Set the human name (e.g. "Qwen Code")
  swe edit <name> --version=<ver>      Set version string
  swe edit <name> --notes="..."        Set notes
  swe edit <name> --primary-color=#RRGGBB  Set the brand colour
  swe edit <name> --set=field=value    Compact multi-set form
  swe edit <name> --notes= --json      Apply the flags, print the result as JSON

  Editable fields: command, display name, description, aliases, tags,
  version, notes, primary color. The display name is how the app (and swe info)
  names the harness; the registry name and command stay what they are.
  --primary-color accepts #RRGGBB or RRGGBB and stores it uppercase; an
  empty value drops the entry's own colour so the catalog default shows
  again. --display_name and --set=display_name=... work too.
  With no field flags, opens an interactive prompt loop (save / quit).
  An empty value clears a field: --display-name=, --version=, --notes= and
  --primary-color= become unset,
  --description= becomes "", --aliases= and --tags= become [].
  Alias collisions with other tools are rejected.
  With --json it never prompts: no field flag is an error, and every
  refusal (unknown harness, alias collision, empty command, unknown flag)
  prints a message on stderr, nothing on stdout, and exits 1. Success prints
  {"name", "changes", "harness"}, where harness is the swe list --json row.

Examples
  swe edit mastracode
  swe edit mastracode --description="Mastra Code — AI coding agent" --aliases=mc
  swe edit droid --set=tags=agentic,coding,autonomous

swe remove (rm)

Remove a tool from the registry

  swe remove <name|alias>      Remove by name or alias
  swe rm <name|alias>          Same as remove

  Does not uninstall the tool, only removes it from the registry.
  See swe help add for what the registry is.

swe check

Verify install status and refresh versions

  swe check                    Probe each tool for live version

  Tries version / --version / -v / -V flags.
  Stores bare version numbers only (no tool-name prefix).
  Also warns about off-PATH installs (e.g. nvm globals invisible to swe).
  Updates registry if version changed.

swe harness (hs)

Everything about the harnesses you have

  swe harness list                  List them  (swe list is the shortcut)
  swe harness edit                  Review every harness at once
  swe harness star <name>           Toggle a favourite
  swe harness archive <name> [why]  Shelve one you have ruled out
  swe harness discover              Scan PATH and home dirs for AI tools (dry-run)
  swe harness discover --apply      Add high-confidence matches to harness.json
  swe harness discover --apply-all  Add every match, including low-confidence finds
  swe harness discover --json       Machine-readable output
  swe harness discover --all        Include already-registered and missing tools too
  swe harness usage <devin|cursor> --account-dir=<dir>  An extra account's rate
                                                   limit, from its own credentials (add --json)
  swe harness usage-events cursor [--account-dir=<d>] [--since=<s>]
                                                   Cursor's per-event feed (add --json); status
                                                   "incomplete" means part of the window hit the
                                                   page cap
  swe harness usage-daily codex [--account-dir=<d>]  A Codex account's per-day
                                                   usage via `codex app-server` (add --json);
                                                   status is ok / auth-required / unsupported /
                                                   unavailable

Alias  swe discover is the same as swe harness discover

swe discover

Scan PATH and home dirs for unregistered AI tools

  swe discover [--apply]   Alias for swe harness discover

  See swe help harness for flags (--apply, --apply-all, --json, --all).

swe use (run)

Launch a tool (replaces current process)

  swe use <name|alias> [args]  Launch a registered tool
  swe run <name|alias> [args]  Same as use

  Extra args are passed through to the underlying command.
  Uses os.execvp to replace the process cleanly.

Examples
  swe use cc

  swe use gemini -p 'explain this codebase'

Analytics

swe session

Show recent AI sessions across all agents

  swe session                  Show last 10 sessions
  swe session <N>              Show last N sessions
  swe session use <N>          Resume session #N
  swe session -i               Pick with arrow keys; space reads a transcript, Enter resumes
  swe session index            Index agent transcripts for --search
  swe session index --on|--off Whether the remote hub keeps the index current
  swe session index --status   What the index holds, without a pass

Flags
  --agent=<name>               Filter by agent (claude, codex, opencode, droid, ...)
  --here                       Filter to current directory only
  --search=<text>              Filter title/path/agent/session id, and transcript
                                            content when a search index exists (the Quiver
                                            app's, or swe session index) (alias: -q, --grep)
  -d N, --days=<N>             Include today and the preceding N-1 calendar dates
  -w N, --weeks=<N>            Include the latest N times 7 calendar dates
  -s, --start=<YYYY-MM-DD>     Inclusive range start; use together with --end
  -e, --end=<YYYY-MM-DD>       Inclusive range end; use together with --start
  -i, --interactive            Pick with arrow keys; Enter resumes, space opens the transcript
  --json                       Print the listing as one JSON document; not with use or -i

Examples
  swe session
  swe session 20
  swe session use 3
  swe session -i
  swe session --agent=claude
  swe session --here
  swe session -d 5
  swe session -w 3
  swe session -s 2026-07-01 -e 2026-07-30
  swe session --search=login
  swe session 30 -q refactor
  swe session index --on

swe report

Summarize coding sessions and manage follow-ups

  swe report daily              Preview and generate a daily coding-session report
  swe report weekly             Preview and generate a weekly coding-session report
  swe report warnings <manifest> Print warnings recorded for one specific report
  swe report followups                     List open follow-ups
  swe report followups --status=open|done|dismissed  Filter by status (default open)
  swe report followup done <id>  Mark a follow-up done manually
  swe report followup work <id>  Resume its source or start a contextual session

Before any model runs, SWE displays session counts, exclusions, cache hits,
planned calls, and estimated input tokens. Normal plans ask for y/N. Plans over
configured limits require the exact phrase process all.
When a report completes with warnings, SWE prints the exact
swe report warnings <manifest.json> command for that report.

Source flags
  -d N, --days=<N>              Override the report with N calendar dates
  -w N, --weeks=<N>             Override the report with N times 7 calendar dates
  -s, --start=<YYYY-MM-DD>      Inclusive custom start; requires --end
  -e, --end=<YYYY-MM-DD>        Inclusive custom end; requires --start
  --here                        Include only the current project
  --agent=<name>                Include only one coding harness
  --search=<text>               Match session title/path/agent/id (alias: -q)

Reports run in two passes: a cheap model summarizes each session, then a
stronger model writes the final report from those summaries. The flags below
pick the harness/model for each pass; leave any of them out and SWE falls
back to report.session.* / report.writer.* in swe config.

Runner override flags
  --session-harness=<name>       Cheap summarizer harness: claude or codex
  --session-model=<model>        Model used for project/session summaries
  --session-arg=<arg>            Pass one extra summarizer argument; repeat as needed
  --writer-harness=<name>        Harness used for the final report
  --writer-model=<model>         Strong model used for the final report
  --writer-arg=<arg>             Pass one extra writer argument; repeat as needed

Follow-up actions
  add <text> [--project=PATH]  Add an item; project defaults to the current directory
  edit <id> <text>             Correct an item's text
  done|dismiss|reopen <id>     Change status explicitly
  work <id> --resume           Resume the newest referenced supported session
  work <id> --new --harness=X  Start a new contextual session with harness X

swe models

Show model usage across all tools

  swe models                   Flat list, model name only, sorted by count
  swe models -t                Group by tool
  swe models -p                Show provider prefix (e.g. openai/gpt-5.4)

Flags

Remote

swe remote

Watch and steer sessions from a phone

  swe remote serve [--host=H] [--port=N]   Run the hub: session catalog,
                                            transcript tailers, REST + SSE for
                                            the phone app. Binds this machine's
                                            Tailscale IP by default.
  swe remote serve --public-url=URL      Run behind tailscale serve: binds
                                            127.0.0.1, trusts serve's client
                                            headers, and hands phones URL.
  swe remote serve --install             Keep the hub running: a LaunchAgent
                                            on macOS, a systemd user unit on
                                            Linux. Starts at login or boot,
                                            restarts if it exits. --uninstall
                                            stops and removes it.
  swe remote setup [--apply]             Check every step to a paired phone:
                                            Tailscale, MagicDNS, HTTPS, the
                                            certificate, the hub, tailscale
                                            serve. --apply does SWE's part.
  swe remote pair [--name=N]             Mint a one-time pairing token;
                                            prints the URL to open on the phone
                                            (and a QR when qrencode is installed).
  swe remote status [--host=H]           Probe the hub, list machines
                                            and paired devices.
  swe remote devices [--revoke=<id>]     List or revoke paired devices.
                                            --requests lists pending
                                            pair requests; --approve=<code>
                                            and --deny=<code> decide one;
                                            --request-id=<id> holds the
                                            code to that one request.
                                            --auto-approve=on|off lets
                                            your own untagged tailnet
                                            devices pair without a code
                                            (off by default).
  swe remote attach <session>            Take an observed session
                                            under supervision. Default
                                            --mode=auto picks the
                                            harness's API channel (opencode
                                            serve, codex app-server) when the
                                            binary exists, else relaunches in
                                            tmux with resume flags.
                                            --mode=headless sends
                                            each prompt via claude -p instead.
                                            --model=<m> and
                                            --effort=<e> pick the
                                            launch tuning the channel can
                                            honour (tmux/headless/serve/
                                            appserver take model).
  swe remote agent --hub=URL [--token=T]   Satellite: pushes this
                                            machine's catalog + transcript
                                            events to the hub and runs the
                                            commands it queues. Pair once with
                                            a token, then keep it running —
                                            outbound only, nothing listens.
  swe remote agent --install             Keep the satellite running: its
                                            own LaunchAgent or systemd user
                                            unit, apart from the hub's.
                                            Refused on a machine whose hub is
                                            installed. --uninstall removes it;
                                            --status [--json] shows it.

  The phone only ever talks to the hub, over Tailscale. Sessions list as
  observed (a human terminal owns them: read-only) until they run
  under quiver's supervisor, which marks them attached and writable.

  swe remote notify --ntfy=<url> --topic=<t>  Push notifications via a
                                            self-hosted ntfy: needs-you, finished,
                                            error. Approval prompts get lock-screen
                                            Allow/Deny buttons posting back over
                                            the tailnet. --off disables.
                                            --service-status=on also pushes when
                                            a model provider or agent platform
                                            starts or ends an incident.

  swe remote ssh [--on|--off]            The phone's SSH console, for when
                                            the hub itself is down. It dials
                                            this machine's sshd over the
                                            tailnet, not the hub. --on
                                            writes each paired phone's key into
                                            ~/.ssh/authorized_keys (one tagged
                                            line per device; revoking a device
                                            removes it), --off removes them.

  State lives under ~/.swe/data/remote/: device credentials in
  devices.json (0600), per-session event journals and transcript cursors.

swe sync

Commit, merge and push the ~/.swe hub repo

  swe sync                   Commit local changes, merge the remote in, push,
                             then re-link every harness when content came in
  swe sync --dry-run         Fetch and show what would happen, change nothing
  swe sync status            Branch mode, ahead/behind, uncommitted changes
  swe sync status --fetch    Fetch the remote first

  Device mode, on a device/<machine> branch: merges origin/device/<machine>
  and then origin/main into it, and pushes the device branch only.
  Single-branch mode, on any other branch: merges origin/<branch>, pushes it.

  Every merge is tried first without touching the repo. On a conflict sync
  lists the files and stops with ~/.swe exactly as it was. It never
  force-pushes, and never commits secrets/, cache/, data/ or anything else
  swe's .gitignore lists, even when the hub's own .gitignore is older.

  Both take --json for the app's document.

swe find

Show where shared assets live and what links to them

  Run this when a skill, plugin, or MCP server is not showing up somewhere
  and you want to know why.

  swe find                   Counts for every view below
  swe find amd               AGENTS.md and every harness pointing at it
  swe find skills            Skills, plugins, and every harness skill root
  swe find plugins           Plugins across every plugin-capable harness, and
                             where ~/.swe/plugins drifted from claude and codex
  swe find mcps              MCP servers in the hub, and which harnesses have them
  swe find skills --full     List every path, not just the counts
  swe find plugins -i        Browse them: arrows to move and descend, q to quit
  swe find amd --scope=all   Include project and vendored files
  swe find --harness=all     Include archived harnesses too

Scope  --scope=global|local|all, default global
  global   loaded into every harness session (for plugins: installed
           and enabled; a cached copy with no install record is not)
  local    project files only
  all      both, plus vendored plugin and extension copies

  Collision: swe list also has a --scope, but it means something else there
  (active/archived/all harness visibility, not where a file lives).

Harness activity  --harness=active|all, default active, every view
  active   hides rows whose harness is archived in harness.json
           (starred still counts as active — it is only pinned, not shelved)
  all      shows archived harnesses' rows too

  A row hidden this way is never silent about it: the listing ends with
  N archived harnesses hidden; --harness=all to show. A row that cannot
  be mapped to a harness in harness.json — the shared quiver copy, an
  unregistered config — is never filtered, active or not: unknown is the
  one thing swe find exists to keep visible.

  Which harnesses get walked, and where each one's files live, comes from
  harness.json's own capabilities first — the per-harness field in
  harness.json recording what a tool supports (skills? plugins?) and where —
  and only falls back to a hardcoded guess for a harness the registry has
  never heard of.

States
  synced         symlinked to the shared copy
  unsynced       a real directory that could be absorbed
  own copy       a real (non-symlink) file, not pointing at the shared one
  separate       holds content that exists nowhere else, left alone
  wrong target   symlink pointing somewhere unexpected
  in the way     a real file where a link should be
  not installed  harness absent from this machine

  Same ideas swe list and swe init print under different names:
  linked=synced, create=missing, relink=wrong target, conflict=in the way.

  Read-only. swe init is what changes anything.

swe plugins

Every plugin in every marketplace, and install it per harness

  swe plugins                       Every marketplace claude, codex or cursor has registered
  swe plugins catalog <marketplace>   One marketplace's plugins and their state per harness
  swe plugins catalog --json          The whole catalog as JSON (the app's Plugins page)
  swe plugins install <ref> --harness=claude|codex
  swe plugins uninstall <ref> --harness=claude|codex
  swe plugins enable <ref> --harness=claude|codex
  swe plugins disable <ref> --harness=claude|codex
  swe plugins marketplace add <source> --harness=claude,codex

  A ref is <plugin>@<marketplace>, the name both CLIs use. The catalog
  lists installed and uninstalled plugins alike, plus anything installed
  whose marketplace has no readable manifest. It reads files only, never
  the network: a marketplace shows what its last fetch left on disk.

Actions  Each one checks first and does nothing if the plugin is
  already in that state, then runs the harness's own CLI:
  claude   claude plugin install|uninstall|enable|disable <ref>
  codex    codex plugin add|remove <ref>
  Codex has no enable verb, so enable and disable set
  [plugins."<ref>"] enabled in ~/.codex/config.toml, an edit swe checks
  parses back to the same file with only that flag changed. When it cannot
  prove that, it writes nothing and says what to edit by hand.
  Cursor is read-only: it keeps no install record swe can read.

  Collision: swe find also has a --harness, but it means active|all there.
  swe find plugins shows drift between ~/.swe/plugins and each harness.

swe hooks

Manage the hook scripts under ~/.swe/hooks

  swe hooks                       Every hook, its tier, link state, declaration
  swe hooks list [--harness=<h>]  One harness only
  swe hooks info <name>           One script: path, docstring, state, events
  swe hooks edit <name>           Open the hub file in VISUAL or EDITOR (default vi)
  swe hooks new <harness> <name>  Write a Python skeleton + the stanza to paste
  swe hooks new shared <name>     Same, but the shared normalized contract
  swe hooks check                 Declared-but-missing, linked-but-undeclared,
                                    or a hub script never linked in
  swe hooks sync                  Regenerate shared wrappers, re-apply links
  swe hooks disable <name>        Unlink a hook without deleting it
  swe hooks enable <name>         Re-link a disabled hook
  swe hooks delete <name>         Remove the hub file (--foreign: the real file;
                                    --yes skips the confirmation)

Tiers
  shared    ~/.swe/hooks/shared/<name>.py — one script deployed
           into every installed shim-able harness through a generated
           wrapper (hooks/<h>/_generated/). Its # events: [PreToolUse, ...]
           header says which normalized events it wants.
  harness   the per-harness scripts swe links into each hooks root
  foreign  a script or declared command no ~/.swe source claims —
           another installer owns it; swe lists it, never writes it

  Scripts live one folder per harness under ~/.swe/hooks/, and
  swe init links each into that harness's hooks dir (~/.claude/hooks,
  ~/.factory/hooks, or capabilities.hooks.root in harness.json).
  The contract registry (events, schema, settings file, quirks like
  cursor's must-print-JSON and codex's trusted command hashes) lives in
  hooks/contracts.py; harness.json capabilities.hooks entries override it.

  Declaring a hook — the event, matcher and timeout in settings.json or
  hooks.json — stays with you: swe reads those files for the DECLARED
  column and swe hooks check, but never writes them, and
  delete never removes a stanza.

States
  linked    already points at the hub copy
  create    nothing at the destination yet (swe init links it)
  relink    symlink points elsewhere
  conflict  a real file is in the way, needs swe init --force
  skipped   no hooks root, or harness not installed
  ignored   .linkignore, archived in harness.json, or disabled
  foreign   not managed by swe — list-only

GitHub

swe gh

GitHub surfaces: PRs, issues, actions, inbox, pinned repos

  swe gh                          gh status + pinned repos
  swe gh sync                     Snapshot your repos + orgs into the
                                            local catalog (resync-only updates)
  swe gh repo list|add|remove|reorder|search   The repos the dashboard watches
                                            (search reads the catalog, then live;
                                            --all is public)
  swe gh board [--repo=R]            Every surface of a repo in one call
  swe gh pr [--repo=R] [--state=S]     Pull requests (default: open)
  swe gh pr status                Current branch, authored, needs-review
  swe gh pr view <N>              One PR: checks, reviews, merge state
  swe gh pr merge <N> [--method=M] [--auto]
                                            Merge a PR (default: squash)
  swe gh pr worktree <N>           Checkout the PR head under
                                            ~/.swe/worktrees (a session's
                                            launch point)
  swe gh issue [--repo=R]          Issues
  swe gh issue view <N>           One issue: body, comments, and the
                                            prompt an agent resolving it gets
  swe gh issue comment <N> --body=TEXT
                                            Comment on an issue as you
  swe gh issue worktree <N>       Branch quiver/issue-N off the default
                                            branch, checked out under
                                            ~/.swe/worktrees
  swe gh run [--repo=R]            Workflow runs (alias: actions)
  swe gh run rerun <id> [--failed]  Re-run a workflow run
  swe gh pages [--repo=R]          GitHub Pages site + latest build
  swe gh releases|tags|branches    Auxiliary repo surfaces
  swe gh inbox                    Your GitHub notifications
  swe gh inbox read <id>...|--all   Mark notifications read

  Repo resolution: --repo=owner/name wins, else the working
  directory's git remote, else every pinned repo. So a bare
  swe gh pr inside a checkout shows that repo; outside one it
  shows all pinned repos in turn.

  Flags
  --repo=owner/name   Repo (a github.com URL works too;
                          comma-separate several: --repo=a/b,c/d)
  --state=open|closed|…  pr: open/closed/merged/all; issue: open/closed/all
  --limit=N            Rows to fetch (default 30, cap 200)
  --all                inbox: include read notifications
  --web                Open the matching github.com page instead
  --body=TEXT          issue comment: the comment, as one argument
                          (it reaches gh on stdin, so any text is safe)
  --body-file=PATH|-   issue comment: read the comment from a file,
                          or stdin with -, so it never shows in ps
  --json               {schema, data} envelope; data is
                          {github: {status, login}, results: [...]} with one
                          entry per repo: ok → rows, else a typed status
                          (not-found, upstream-error) plus the error text

  Auth is ambient: swe gh uses your gh auth login and never
  stores tokens. The few writes (merge, rerun, inbox read, issue comment)
  are explicit commands, never side effects of a read.

Shell

swe autocomplete

Generate and inject shell completion script

  swe autocomplete zsh    Generate + inject zsh completion
  swe autocomplete bash   Generate + inject bash completion
  swe autocomplete fish   Generate + inject fish completion

  Writes a completion script to ~/.swe/completions/ and adds a
  source line to your shell profile (~/.zshrc, ~/.bashrc, or fish config).

  After running, restart your terminal or run:
    source ~/.zshrc  (or the equivalent for your shell)

  The completion script calls swe __complete under the hood to
  provide dynamic completions for tool names, aliases, tags, and flags.

swe version

Print the swe version

  swe version    swe -v    swe --version

  Prints the installed version and exits. Reads no config, so it works even
  when ~/.swe is broken. --json emits the standard envelope:
  name, version and the Python version under `data`.

swe bug

Report a bug on GitHub, versions filled in

  swe bug              Open the bug form in your browser with the
                       swe, Python and OS versions filled in
  swe bug --feature    Open the feature-request form instead
  swe bug --print      Print the link instead of opening it

  Nothing is sent until you submit the form on GitHub. Paste
  swe doctor output into it when doctor reports a problem.
  --json prints kind, url, version and os under `data` and opens
  nothing. The Mac app's Help › Report a Bug opens the same form.
